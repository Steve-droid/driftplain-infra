## Revert procedures

The migrations are additive, but they are one-way in practice: do not run `alembic downgrade`.
Pick the smallest revert that fixes the problem.

1. **Frontend-only bug.** Revert the frontend pin in `charts/modelmatch/values-home-server.yaml`
   to frontend 2.0.0 (`ghcr.io/steve-droid/driftplain-frontend@sha256:5c1f176326a1443ad726aef8a6116a7de1402bd3416dcda1872dbc8422b9b0ce`)
   through a GitOps PR. The 1.0.26 frontend cannot be used with backend 2.x: its weighted
   create/re-pick calls receive HTTP 410.
2. **Backend-only bug.** Pin backend 2.0.0
   (`ghcr.io/steve-droid/driftplain-backend@sha256:ff4c915aa636dd747525fd2ea18df81243417d560cb8fd865e1df6d22a73061a`);
   it serves the same schema head. Imported DeepSWE rows stay in the database; reading them is
   data, not code.
3. **Full return to 1.0.25 / 1.0.26.** Image pins alone are not a safe revert, because
   1.0.25 predates B6 and cannot be assumed to serve explicit projects written by 2.x. Revert the
   GitOps pin PR **and** restore the pre-migration export into an emptied production database
   with `home-server-database.py restore --target production` (HM3-RESTORE.md). This discards
   every write made after the export. It needs Steve's explicit approval at the time.
